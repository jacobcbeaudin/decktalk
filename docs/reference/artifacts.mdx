title: Build artifacts
description: Every file DeckTalk keeps under build/ today, what each one is for, and how the engine reads it. The promised part is the stability promise.
---

Everything a run generates lives under one directory. `[project] build` names it, and it is `build/`
unless the project says otherwise. Nothing under it is written by hand, and deleting the whole of it
costs only the time to make it again. The paid records never live under `build/`. The voiced takes
and the words their voice sent back live in the takes directory, `takes/` unless
`[narration] takes_dir` names another, which you commit, with a second copy in the machine's take
store, `[narration] store_dir`. The bought sounds and the ledger that lists them live in the score
directory, `score/` unless `[score] dir` names another, which you commit too. The take index, the
placeholders, the joined narration and the joined music stay under `build/`, because a build makes
them again for nothing.

This page describes the engine as it is, and most of it is a private cache. What DeckTalk promises a
caller is [the stability promise](/reference/stability): the `--json` results, the events file, `build/final/`
and the exit codes. A shape on this page can change in any release, and a script that reads a cache
file reads something nobody promised it.

Every file a stage writes a shape for is a frozen model, so the field names below are the JSON keys
and the model both reads and writes the file. A file is written under a temporary name in the same
directory and renamed over the target, which is atomic on every platform DeckTalk ships on, so a
reader never opens a half-written artifact and an interrupted run leaves the previous file whole. A
cache file that is there and will not parse, including one an older release wrote, is built again by
the stage that writes it. A paid record that will not parse is refused with a sentence and left
where it is, because building it again would buy it again. The take index is not a paid record,
because it is read again off the takes on disk.

## Finding an artifact without knowing a path

Every result whose command writes files declares `written`, which carries the project-relative path
of each file that run wrote, in the order it wrote them. That is how a caller finds an artifact
rather than by spelling a path.

```bash
uv run decktalk narrate --json | python -c "import json,sys; print(json.load(sys.stdin)['written'])"
```

```python
import decktalk

project = decktalk.open("my-lesson")
result = project.narrate()
for path in result.written:
    print(path)
```

The same rule holds everywhere: a path DeckTalk publishes is relative to the project root and
spelled with forward slashes on all three platforms.

## The tree

The takes a voice spoke and the sounds the score bought are not under `build/`. They sit in the
takes directory and the score directory, which you commit:

```
my-lesson/takes/
  <digest>.mp3                    one take, named by the content that produced it, under the suffix of
                                the format its voice declares, which is .mp3 for ElevenLabs
  <digest>.words.json             that take's words, in seconds after the take starts, with the size
                                and BLAKE3 of the take they came with
my-lesson/score/
  ambience.mp3                  the ambience bed, when the project declares one
  <name>.mp3                    one file per declared effect
  music-part<n>.mp3             each part of the music bed, when the project declares one
  ledger.json                   what this project has already bought, keyed by the request that made it
```

Each sound is named by its item, so `--replace-score` with `--spend` writes over the same file.

A take stays in the takes directory after the script moves on from it, such as after a voice change.
`decktalk status` lists the takes there that no section plays, and any aligned words under
`aligned/`, with their size, and `--json` carries them as `unplayed`. DeckTalk never deletes one,
so remove the ones you no longer want with `git rm`. A take counts as played when the take index or
a section's current text, voice and settings name it, and with no voice named `unplayed` is null.

Everything else a run writes is under the build directory:

```
my-lesson/build/
  narrate/
    takes.json                  which section plays which take, and the clock the join makes
    placeholder-<digest>.mp3      a placeholder for a section with no voiced take yet
    placeholder-<digest>.words.json  its estimated words
    narration.mp3               the takes joined into one track, which assemble mixes under the picture
  cue-times.json                every cue resolved to a second on its own section's clock
  recordings/
    NN.webm                     one section as the browser recorded it
    NN.json                     what record did for that section, judged and measured
  score/
    music.mp3                   the music bed joined from its parts, when the project declares one
  sections/
    NN.mp4                      one section video, encoded to its own span, which assemble concatenates
    NN.json                     the key that video was encoded from, which decides whether it is kept
  stills/
    <key>.png                   one frozen frame, named by everything that decides how it looks
    <key>.json                  the project files the page had loaded when that frame was drawn
  frames/
    NN/<state>.png              the frozen slides check compares either side of a cue
  storyboard/
    NN/<state>.png              the stills the storyboard page lays out
  storyboard.html               the contact sheet a person reads before any credit is spent
  final/
    <name>.mp4                  the film
    <name>.srt                  the captions, as SubRip
    <name>.vtt                  the captions, as WebVTT
    <name>.chapters.txt         the chapter markers, as ffmetadata
    <name>-transcript.html      the whole film as one page, which is the media alternative
    <name>-poster.png           the opening slide as a lossless PNG
    placements.json                   where every section sits in the finished film
  events/
    <run>.jsonl                 one JSON line per event of one run
  kept.json                     what the last assemble and verify read, wrote and found
  .lock                         locked by the one run that is writing, and left in place
  .lock.owner                   the process and the run holding the lock, removed when it ends
```

`<name>` is `[project] name`, which is what the film is named after. `NN` is a section's key, which
is its number padded to two digits, so section 3 is `03`. `<run>` is the twelve hex characters that
name one run.

Three of those are not artifacts in the sense of a file a later stage reads. `frames/` and
`storyboard/` are pictures for a person and for a comparison. `events/<run>.jsonl` is what a run said
while it ran, appended by a subscriber to the event stream rather than written by a stage.

## `build/narrate/takes.json`

The take index is the time base every later stage measures against. It says which section plays
which take, and the rows are enough to work out where each section sits in the joined narration, so
the file cannot hold a total that disagrees with what it lists.

It is a cache, not a paid record. Every field of a row is read again off the script, the settings and
the take and words files its digest names, so `narrate` builds an index that will not parse again
from the takes on disk, keeps every take it finds and buys nothing for it.

```json build/narrate/takes.json
{
  "script": "script.md",
  "model": "eleven_multilingual_v2",
  "output_format": "mp3_44100_128",
  "sections": [
    {
      "section": 1,
      "key": "01",
      "chapter": "Open",
      "digest": "9f2c1ab7d4e60518",
      "voiced": true,
      "word_count": 38,
      "characters": 200,
      "estimated_seconds": 16.3,
      "duration_seconds": 18.1,
      "speech_end_seconds": 17.98,
      "sound_end_seconds": 17.987,
      "lead_seconds": 0.5,
      "tail_seconds": 1.3,
      "spoken": "This is DeckTalk. Four files sit in one folder, and you write two of them."
    }
  ]
}
```

| Field | Meaning |
|---|---|
| `script` | The script these takes were made from, project-relative. |
| `model` | The provider model every voiced row was spoken by. |
| `output_format` | The audio format every row was asked for in. |
| `sections[].section` | The section this row is about, as the author numbered it. |
| `sections[].key` | The section's key, which names its files under the build directory. |
| `sections[].chapter` | The section's title, which the film's chapter marker carries. |
| `sections[].digest` | The digest of the inputs this take was made from, which names its files. |
| `sections[].voiced` | True when a provider spoke this take, false on a placeholder. |
| `sections[].word_count` | How many words this take speaks. |
| `sections[].characters` | How many characters were sent to the voice, which a per-character bill counts. |
| `sections[].estimated_seconds` | How long the script said this take would run. |
| `sections[].duration_seconds` | How long the audio file runs, measured from its own bytes. |
| `sections[].speech_end_seconds` | Where the last word ends, or null. |
| `sections[].sound_end_seconds` | Where the take's sound ends, or null. |
| `sections[].lead_seconds` | Silence placed before the take, which is not in the file. |
| `sections[].tail_seconds` | Silence placed after the take's sound, which is also not in the file. |
| `sections[].spoken` | The words the voice says, with the script's punctuation, which the captions borrow. |

A section runs for its lead, then its take up to where the take's sound ends, then its tail, and the
sections run in section order. Where each one sits in the joined narration is therefore arithmetic
over the rows rather than a second file that can disagree with them. Each of those three numbers is
a pure function of the take's own bytes and its own section's settings, so a section lands the same
way whether this run voiced its take or found it cached.

### A take is named by a digest of its inputs

A take is identified by its input digest and by nothing else. The index maps a section to a piece of
content and never the other way round, so renumbering a section rewrites one row and moves no file,
and two sections with the same words share one take.

The digest of a voiced take is taken over exactly these, joined by newlines in this order.

| Input | Why it changes the audio |
|---|---|
| `provider` | Two services reading one sentence are two different takes. |
| `voice` | Two voices reading one sentence are two different takes. The voice id is a published name rather than a secret, so it is written into the file a reader can see. |
| `model` | A model changes how the same words are read. |
| `output_format` | The bytes asked for, in the format the provider declares, such as `[elevenlabs] output_format`. |
| `settings` | The take identity the provider declares, `[voice] speed` and its own fields such as `[elevenlabs] stability`, as compact JSON with its keys sorted. |
| `text` | The exact text sent to the voice, with its pause tags. |

Every input but `text` refuses a newline before anything is sent, and `text` comes last, so the
joined payload reads back as exactly one set of inputs and no two sets share a take. The take's file
is named by the digest under the suffix of the format it holds, which is `.mp3` for every ElevenLabs
format.

**This is why an edit voices only the sections whose words changed.** Edit one paragraph of
`script.md` and only that section's text moves, so only that section's digest moves, so `narrate`
sends one request and every other section is found on disk under the name it already had. Change the
voice id or the model and every digest moves, because every take really would sound different.
Adding a field to that list or changing its order would re-voice every project there is, which is
what the digest test in the repository holds it to.

A placeholder take is named the same way over its own three inputs, which are the pace it is sized
at, how long a declared pause is held, and the text it stands in for. Its digest carries the prefix
`placeholder-`, so a run that writes placeholders can never overwrite a voiced take.

## `takes/<digest>.words.json`

Beside every take sits its words file, under the same digest. This is the smallest artifact and the
one every other reads: a cue resolves against it, the captions are built from it, and the clicks of
a placeholder take sit at each `start`.

The words the speech provider sends back with a voiced take are a paid record, because only voicing
the take again gives them back. They are written in one step with the take, and they record the take's
size and BLAKE3 under `audio`, because a take's name says what was asked for and only this fingerprint
can tell a truncated or swapped take from a good one. `audio` also records the suffix the take was
written under, so a take is still found after the voice moves to another format. A copy whose words do
not read, or whose take does not match them, is skipped wherever it is found, moved aside as
`<name>.unreadable` when a good copy replaces it, and never copied or deleted. When no copy anywhere
is good, the run is refused with a sentence, because the next step would buy the take again. Words
DeckTalk estimated for a placeholder take are a cache under `build/narrate/`, like the rest of
`build/`.

```json takes/9f2c1ab7d4e60518.words.json
{
  "words": [
    { "word": "This", "start": 0.0, "end": 0.454 },
    { "word": "is", "start": 0.474, "end": 0.927 },
    { "word": "DeckTalk", "start": 0.947, "end": 1.401 }
  ],
  "audio": { "bytes": 22656, "blake3": "4be0ce1f9a2d7c31" }
}
```

Each row is the same `Word` a result carries, so the file a stage writes and the JSON a caller reads
are one shape. `start` and `end` are seconds after that take starts, which is not the same clock as
the section: the section's own clock begins at its lead.

## `build/cue-times.json`

One block per section, each holding every cue that section declares, resolved against the words it
speaks.

{/* sample: build/cue-times.json after decktalk build --no-spend on a fresh decktalk init my-lesson, cut to the first section's first two cues */}
```json build/cue-times.json
{
  "sections": [
    {
      "section": 1,
      "key": "01",
      "estimated": true,
      "cues": [
        { "id": "1.1:title", "phrase": "This is DeckTalk", "seconds": 0.5, "nudge_seconds": 0.0 },
        { "id": "1.1:files", "phrase": "Four files", "seconds": 1.921, "nudge_seconds": 0.0 }
      ]
    }
  ]
}
```

| Field | Meaning |
|---|---|
| `sections[].estimated` | True when the seconds come from estimated words rather than a voiced take. |
| `sections[].cues[].id` | The cue's cue id, which is its slide, a colon and the cue name the page writes. |
| `sections[].cues[].phrase` | The phrase in the script this cue lands on. |
| `sections[].cues[].seconds` | When it lands, in seconds after its section starts, or null when it did not resolve. |
| `sections[].cues[].nudge_seconds` | The author's own nudge in seconds, which is already inside `seconds`. |

The recorder passes these seconds to the page as the `cues` query, so a cue with no second behind it
is left out of that value rather than passed as a null the page would have to reason about. A page
previewed in a browser has no such URL, so the local origin answers one alias from this file
instead.

## `build/recordings/`

`record` writes two files per page section, both named by the section's key.

`NN.webm` is the recording as the browser produced it. `NN.json` is the recorder's whole account of
that section, written when that section is finished, so a reader of a long run sees each section's
log as soon as that section is done and a measurement always belongs to the recording beside it.

{/* sample: build/recordings/01.json after decktalk build --no-spend on a fresh decktalk init my-lesson, with the report's five lists cut to [] */}

|---|---|
| `section` | The section this recording plays. |

| `start.guessed` | True when no cover was found, so every reveal in the section moves. |

| `checks` | What the frames measured, or null when none were. |

Every judgement the recorder makes is a finding, so the page's own warnings, the exceptions it threw
and the checks over the frames are one list a reader dispatches on by code.

`digest` is what decides whether a section is recorded again. It is taken over the page URL with
its cues and its words, the frame geometry, the markup of the one scene the section plays, the rest
of its page, which every scene shares, and the content of every file the page loaded. A section
whose digest is unchanged would be recorded again for nothing, so it is kept.

`report` is what the page answered `window.__dtprobe.report()` with, kept whole.
[Runtime](/reference/runtime) gives every field of it.

## `score/ledger.json`

The score directory holds one audio file per sound the `[score]` table declares, named after the
item unless the table sends it elsewhere. The ambience bed is `ambience.mp3`, each effect is named
after the key it is declared under, and the music bed is bought in parts, `music-part1.mp3` and on,
which are joined into `build/score/music.mp3`. A run that finds the parts and not the joined piece
joins them again, which buys nothing.

Beside them is `ledger.json`, which is what this project has already bought.

```json score/ledger.json
{
  "items": [
    {
      "name": "music",
      "kind": "music",
      "digest": "7c04a1ee39b2d5f8",
      "file": "build/score/music.mp3",
      "seconds": 96.0,
      "parts": ["3ab1d0f27c845e69", "9de2b61840cf37a5"],
      "request": "{\"chunks\":[{\"prompt\":\"a slow warm pad\"}],\"crossfade_seconds\":1.5}"
    }
  ]
}
```

| Field | Meaning |
|---|---|
| `items[].name` | What the author calls this item in `decktalk.toml`. |
| `items[].kind` | `music`, `ambience` or `effect`. |
| `items[].digest` | The digest of the request this file was made from, which is the endpoint as the sound provider publishes it and the body, and never `base_url`. |
| `items[].file` | The audio this request produced, project-relative. |
| `items[].seconds` | How long that audio runs, or null when unmeasured. |
| `items[].parts` | The digest of each music part, in the order they are joined, and empty for a single request. |
| `items[].request` | The request body as compact JSON with its keys sorted, so a reader sees what was asked for. |

Every request is paid for, so the one question this file answers is whether the audio on disk was
made from the request the project asks for now. A row whose digest still matches is kept rather than
bought again. It is one file for the whole score rather than a cache file beside every output,
because the outputs may sit wherever `decktalk.toml` sends them and a run has to read the whole
record before it prices anything. A ledger that is there and will not parse, including one an older
release wrote in another shape, is refused with a sentence and left on disk rather than read as a
project that has bought nothing, because moving it aside is a decision about money and so it is the
author's to take.

## `build/sections/`

One section video per section, encoded to the span the take index gives it, which is what `assemble`
concatenates into the film. A section video left behind by a renumbering belongs to no section, and
`assemble` names each such file rather than folding it into a film nobody asked for.

Beside each section video, `NN.json` holds the key it was encoded from.

{/* sample: build/sections/01.json after decktalk build --no-spend on a fresh decktalk init my-lesson */}
```json build/sections/01.json
{
  "digest": "5d584d9c228cd63e785d2a8788dfc94227a6359612dd5e621c28f0a860382580"
}
```

The digest is a sha256 over the whole argument list of the encode, the BLAKE3 digest of every file it
read and the engine version. `assemble` keeps a section video whose key still matches rather than
encoding it again, so an edit to one section encodes that section again and leaves the others alone.
Nothing chooses which arguments count, because a key over a hand-picked subset would one day miss an
input and ship a stale picture, and a new engine version encodes every section again because it may
encode the same arguments differently.

## `build/stills/`

Every frozen frame `check`, `storyboard` and the poster draw, kept by what drew it, so one state of
a page is drawn once whichever of the three asks for it first. `<key>.png` is named by a digest of
everything the caller knows before the page opens: the URL, the frame size, the colour scheme, the
motion settings, the content of the page file and the engine version. `<key>.json` beside it names
every project file the page went on to load, with its digest then, because a picture or a module the
page reached for is part of the picture too.

A still is used only when its key matches and every file its manifest names still has the digest it
had, which is the same rule the recorder applies to a whole section. So a second `check` on an
unchanged deck opens no page for a frame it already has, and an edit to one picture draws again only
the frames that loaded it.

The slate that stands in for a missing clip is kept here too. Its key is everything it shows: the
chapter title, the lines above and below it, the frame size, `[video] slate_color`, the page policy
and the engine version. A renamed chapter or a new colour therefore draws a new slate, and the section
cut that reads it gets a new key.

A frame nobody has found or kept for a fortnight is removed whenever another is kept, so the frames
of an edited page and the slates of a renamed chapter do not stay for as long as the project does.

## `build/kept.json`

The record a build leaves of its last `assemble` and `verify`, which is what lets the next build keep
them. For each stage it holds the digest of everything the stage read with the options it ran with,
the digest of every file it wrote, and every finding it made.

| Field | Meaning |
|---|---|
| `assemble.digest`, `verify.digest` | The digest of everything the stage read, with the options it was run with. |
| `assemble.options`, `verify.options` | The options the stage was run with, as the build passed them. |
| `assemble.outputs`, `verify.outputs` | Each file the stage wrote, project-relative, against the digest of its bytes. |
| `assemble.findings`, `verify.findings` | What the stage found, which a build that keeps the stage reports again. |

A build whose digest for a stage matches, and whose outputs still hold those bytes, keeps that stage
rather than running it. `assemble` and `verify` are pure functions of files already on disk, so the
film on disk is the one they would make and the measurement is the one they would take. The stage is
reported with the outcome `kept`, its findings are reported again, and `--force` runs it anyway.

The digests are over file contents and never over file times, because a copy or a checkout moves
every time and changes no byte. Only `build` writes this file, so after a `verify` run on its own,
`status` still names `verify`. A record this version cannot read keeps nothing, which costs one
assemble and one verify and is never wrong.

## `build/final/`

Everything a viewer receives. `<name>` is the project name.

| File | What it is |
|---|---|
| `<name>.mp4` | The film, written under a work name and renamed into place only once it is whole. |
| `<name>.srt` | The captions as SubRip, built from the words files with a bracketed line for each sound the mix adds. |
| `<name>.vtt` | The same captions as WebVTT. |
| `<name>.chapters.txt` | The chapter markers as ffmetadata, muxed into the film. Two sections sharing one chapter share one marker. |
| `<name>-transcript.html` | The media alternative: one page with a heading per chapter, what was said, and the description of each reveal the page reported. |
| `<name>-poster.png` | The opening slide as a lossless PNG, drawn by the page rather than taken out of the mp4. |
| `placements.json` | Where every section sits in the finished film. |

`output.timestamped_copy` writes a second copy of the film beside the first, named with the date and
the minute the copy was taken.

### `build/final/placements.json`

This is the one record of the shape of a film. The transcript page, a caption reader and anything
that wants to jump to a section read it instead of adding section files up.

{/* sample: build/final/placements.json after decktalk build --no-spend on a fresh decktalk init my-lesson, cut to the first section */}
```json build/final/placements.json
{
  "fps": 25,
  "sections": [
    {
      "section": 1,
      "key": "01",
      "kind": "page",
      "start": 0.0,
      "end": 19.8,
      "source": "build/recordings/01.webm",
      "chapter": "Open",
      "substitute": null,
      "dip_in": false,
      "dip_out": false
    }
  ]
}
```

| Field | Meaning |
|---|---|
| `fps` | The rate the film was encoded at. |
| `sections[].kind` | `page` for a recorded page, `clip` for a video file the author supplied. |
| `sections[].start` | When this section starts in the film, in seconds. |
| `sections[].end` | When this section ends in the film, in seconds. |
| `sections[].source` | The recording or the clip this section was cut from. |
| `sections[].chapter` | The section's title, which the film's chapter marker carries. |
| `sections[].substitute` | `slate` or `black` when the real thing was missing, and null otherwise. |
| `sections[].dip_in` | True when the picture dips to black on the way into this section. |
| `sections[].dip_out` | True when the picture dips to black on the way out of it. |

`substitute` says plainly where a slate or a black frame stood in for something the project does not
have. A Python call to `assemble` or `build` with `strict=True` refuses such a section outright,
unless it is a clip whose section declares `optional = true`.

## `build/events/<run>.jsonl`

Every run of a project appends one JSON object per line to its own file, named by its run id. One
file per run, never truncated, so a watch loop running beside a build by hand cannot overwrite what
the other is writing. `--events` prints the same lines on stderr as they happen.

{/* sample: decktalk cue, on a starter built with --no-spend, the whole events file it wrote */}

`event` is the discriminator. `time`, `seq` and `run` are on every line, and `seq` counts per run
rather than per machine, so a reader can tell a gap from a lost line.
[The event stream](/agents/json#the-event-stream) gives every name and every field of every line.

A directory of every run a project ever made would grow without limit, and the runs a caller wants
are the recent ones, so `output.events_keep_runs` prunes the oldest. It defaults to 20 and the
pruning happens as a run opens.

```bash
uv run decktalk config set output.events_keep_runs 50
```

`decktalk status --json` reports every run whose events file is still open, which is how a caller
finds a build running in the background and follows its lines.

## `build/frames/` and `build/storyboard.html`

`check` freezes each slide either side of a cue and compares the two pictures, which is how it says
whether a reveal really changes anything before a single credit is spent. Those pictures are written
to `build/frames/<key>/<state>.png`, where `<state>` names the URL that drew it, such as
`slide-2.1-after-2.1_formula.png`. Each state is drawn once however many cues are measured against
it, because the same URL is the same picture, and each is copied from `build/stills/` when a still of
it is already kept there.

`storyboard` writes its own stills under `build/storyboard/<key>/` with the same naming.

Both commands lay their panels out on one page, `build/storyboard.html`. It sits beside the stills
rather than among them, so a reader opens one file and a rebuild replaces the whole sheet, and one
writer draws it whichever command froze the frames, because two contact sheets of one deck would be
two answers to one question. It is a plain page that needs nothing to open it, with one figure per
panel captioned with its section, its slide, its moment and its second.

## `build/.lock`

A run that writes holds an operating system lock on this file for its whole length, which is `flock`
on Linux and macOS and a byte-range lock on Windows. The system releases it the moment the holder
ends, however it ends, and two writers that race for it cannot both win. While it is held,
`build/.lock.owner` beside it names the process id and the run id, so a second writer is refused
with a sentence that names whose run is in the way. The owner is a note of its own because Windows
refuses a read of a locked file.

`.lock` itself stays on disk after the run, empty. A file removed while another writer waits on it
would let a third lock a new file beside the old one, so deleting it is never needed and never
helps. The holder removes `.lock.owner` when it ends, and a holder that crashed leaves it behind. A
run that finds `.lock.owner` while nobody holds the lock takes the lock and says so, because a caller
cannot clear a note it was never told about.
